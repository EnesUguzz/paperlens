# Configuration reference

Generated by `make explain-config`.

| Parameter | Value | Type | Description |
|---|---|---|---|
| `data.split` | `validation` | Literal | What: QASPER split to evaluate on. Effect: tune everything on 'validation'; run 'test' once for the final table, otherwise test scores become optimistic (eval contamination). |
| `data.sample_size` | `250` | Union | What: number of questions sampled from the split (null = all). Typical: 100-300 while iterating, null for final runs. Effect: higher = less noisy metrics but slower runs; below ~100 questions, differences of 1-2 F1 points are mostly noise. |
| `data.seed` | `13` | int | What: random seed for question sampling. Typical: any fixed integer. Effect: a different seed draws a different subset; keep it fixed so runs are comparable. |
| `data.text_source` | `qasper_text` | Literal | What: where paper text comes from; 'qasper_text' = the dataset's pre-parsed paragraphs, 'pdf_docling' = the arXiv PDF parsed by Docling (run `prepare-pdfs` first; gold evidence is fuzzy-aligned to PDF paragraphs). Effect: measures how parser quality changes retrieval; papers without a parsed PDF are dropped from the evaluation. |
| `data.data_dir` | `data` | Path | What: folder for downloads and indexes (git-ignored). Effect: none on metrics. |
| `data.parquet_url_template` | `https://huggingface.co/api/datasets/allenai/qasper/parquet/qasper/{split}/0.parquet` | str | What: download URL of a QASPER split; '{split}' is replaced. Effect: none. |
| `data.pdf_url_template` | `https://arxiv.org/pdf/{paper_id}` | str | What: download URL of a paper's PDF; '{paper_id}' is replaced by the arXiv id. Effect: none on metrics; only changes where `prepare-pdfs` fetches from. |
| `data.pdf_download_delay_s` | `3.0` | float | What: seconds to wait between two PDF requests. Typical: 3-5. Effect: arXiv's automated-access rule asks for at least 3 s; lower values risk an IP block, higher values only make `prepare-pdfs` slower (cache hits never wait). |
| `data.align_min_score` | `85.0` | float | What: minimum rapidfuzz partial_ratio score (0-100) for a PDF paragraph to count as holding a gold evidence paragraph (text_source 'pdf_docling' only). Typical: 80-95. Effect: lower values accept wrong matches (evidence points at the wrong paragraph); higher values leave more evidence unaligned, which then scores as never found. |
| `data.align_min_words` | `8` | int | What: PDF paragraphs shorter than this many words cannot be alignment candidates (captions are exempt; text_source 'pdf_docling' only). Typical: 5-15. Effect: too low and a fragment such as 'Results' matches every paragraph that contains it; too high and genuinely short paragraphs lose their evidence label. |
| `data.align_score_margin` | `5.0` | float | What: a PDF paragraph only counts as a match if its score is within this many points of the best score for that gold paragraph (text_source 'pdf_docling' only). Typical: 3-10. Effect: lower values drop near-duplicate sibling paragraphs (fewer wrong ids) but can lose the second half of a genuinely split paragraph; higher values keep both. |
| `chunking.strategy` | `fixed` | Literal | What: how papers are cut. 'fixed' = sliding window of chunk_size words that ignores structure; 'section' = whole paragraphs packed up to chunk_size words, never crossing a section; 'semantic' = sentences packed up to chunk_size words, split where neighbouring sentence embeddings diverge (never crossing a section). Effect: 'section' keeps chunks aligned with paragraphs (usually higher Evidence-F1); 'fixed' can split an answer across two chunks; 'semantic' follows topic shifts but costs one embedding pass over all sentences when indexing. |
| `chunking.chunk_size` | `200` | int | What: target chunk length in words (~1.3 tokens per word). Typical: 100-400. Effect: higher -> more context per chunk, Recall@k rises (M1a: 0.70 -> 0.86 at 400) and prompt tokens/latency grow; Evidence-F1 drops mechanically because a cited chunk counts all its paragraphs (compare evidence_f1 to evidence_f1_ceiling). Lower -> sharper matches, but answers may be split across chunks. |
| `chunking.chunk_overlap` | `40` | int | What: words shared by consecutive chunks ('fixed' only). Typical: 10-25% of chunk_size. Effect: higher -> fewer answers cut at a boundary, but more chunks and duplicate text in the prompt. 0 -> smallest index, more boundary misses. |
| `chunking.semantic_breakpoint_percentile` | `90.0` | float | What: 'semantic' only. A chunk is split where the distance between neighbouring sentences exceeds this percentile of the paper's distances. Typical: 80-95. Effect: lower -> more splits and smaller chunks; higher -> only the sharpest topic shifts split (chunks then mostly end at chunk_size). |
| `chunking.semantic_min_words` | `50` | int | What: 'semantic' only. A chunk shorter than this is not split at a semantic breakpoint. Typical: 30-80. Effect: higher -> fewer tiny chunks but breakpoints are ignored more often; must stay below chunk_size (checked for 'semantic'). |
| `chunking.include_section_title` | `True` | bool | What: prefix each chunk with '[Section name]'. Effect: gives the embedder and the LLM structural context ('Results' vs 'Related Work'); usually helps. |
| `chunking.include_captions` | `True` | bool | What: index figure/table captions as paragraphs. Effect: QASPER evidence often points at tables; without captions those questions can never be retrieved. |
| `embedding.model_name` | `BAAI/bge-m3` | str | What: sentence-transformers model for dense vectors; 'hashing' = tiny fake for tests/CI. Effect: stronger models raise Recall@k; bigger ones cost VRAM and indexing time. Changing it rebuilds the index. |
| `embedding.batch_size` | `32` | int | What: passages embedded per GPU batch. Typical: 16-128. Effect: higher = faster indexing until VRAM runs out; no effect on metrics. |
| `embedding.device` | `cuda` | str | What: torch device ('cuda' or 'cpu'). Effect: 'cpu' works without a GPU but indexing is 20-50x slower; no effect on metrics. |
| `embedding.max_seq_length` | `1024` | int | What: max tokens the embedder reads per text; the rest is silently truncated. Typical: 512-1024 (bge-m3 supports 8192). Effect: must exceed chunk_size * 1.5 (checked) or chunk endings are ignored; higher costs memory. |
| `embedding.query_prefix` | `` | str | What: text prepended to queries (e5 models need 'query: '). Effect: a wrong prefix for the chosen model can cost several Recall points. |
| `embedding.passage_prefix` | `` | str | What: text prepended to passages (e5 models need 'passage: '). Effect: same as query_prefix; changing it rebuilds the index. |
| `retrieval.method` | `dense` | Literal | What: 'dense' = embedding similarity, 'bm25' = keyword match, 'hybrid' = both fused with Reciprocal Rank Fusion. Effect: bm25 wins on exact terms (dataset names, metrics, acronyms), dense on paraphrases; hybrid is usually most robust. |
| `retrieval.top_k` | `5` | int | What: chunks passed to the LLM. Typical: 3-10. Effect: higher -> Recall@k up, but more prompt tokens, latency and distracting text (small LLMs may answer worse). Lower -> cheaper, misses multi-part evidence. |
| `retrieval.candidate_k` | `30` | int | What: chunks each retriever returns before fusion ('hybrid'), and the pool size handed to the reranker when rerank.enabled. Typical: 20-100. Effect: higher lets RRF or the reranker rescue items the first stage ranked low; the reranker's cost grows linearly with it. |
| `retrieval.rrf_k` | `60` | int | What: RRF damping constant; score = sum of 1/(rrf_k + rank). Typical: 10-100 (60 is the original paper's value). Effect: lower -> each retriever's top ranks dominate; higher -> rankings are blended more evenly. |
| `retrieval.bm25_k1` | `1.5` | float | What: BM25 term-frequency saturation. Typical: 1.2-2.0. Effect: higher -> repeated query words keep adding score; lower -> one mention counts almost as much as many. |
| `retrieval.bm25_b` | `0.75` | float | What: BM25 length normalisation. Typical: 0.5-0.9. Effect: higher penalises long chunks more; 0 ignores length. |
| `rerank.enabled` | `False` | bool | What: rescore the first-stage pool (retrieval.candidate_k chunks) with a cross-encoder and keep the best retrieval.top_k. Effect: usually raises Recall@k/evidence F1 over plain retrieval; costs GPU time per question. Does not change the index. |
| `rerank.model_name` | `BAAI/bge-reranker-v2-m3` | str | What: sentence-transformers CrossEncoder model; 'lexical' = fake that scores shared words, for tests/CI. Effect: stronger models rank better; bigger ones cost VRAM and latency. |
| `rerank.batch_size` | `16` | int | What: (query, chunk) pairs scored per GPU batch. Typical: 8-64. Effect: higher = faster until VRAM runs out; no effect on metrics. |
| `rerank.max_length` | `512` | int | What: max tokens of a (query, chunk) pair; the rest is truncated. Typical: 512-1024. Effect: should cover chunk_size * 1.5 tokens plus the query or chunk endings are ignored; higher costs memory. |
| `rerank.device` | `cuda` | str | What: torch device ('cuda' or 'cpu'). Effect: 'cpu' works without a GPU but is far slower; no effect on metrics. |
| `query.transform` | `none` | Literal | What: how the question is rewritten before retrieval. 'none' searches with the question itself; 'multi_query' asks the LLM for n_queries paraphrases and fuses their results (RRF); 'hyde' asks the LLM for a hypothetical answer paragraph that the dense search uses (BM25 keeps the plain question). Effect: can raise recall on vocabulary mismatch; costs one extra LLM call per question (latency and tokens are counted in the run); on failure the question itself is used and query_error_rate rises. |
| `query.n_queries` | `3` | int | What: paraphrases kept for multi_query (extra ones are dropped). Typical: 2-5. Effect: more phrasings widen recall but add retrieval work and can dilute the fused ranking; the LLM call count does not change. |
| `query.include_original` | `True` | bool | What: keep the original question among the search texts (multi_query: in both channels; hyde: in the dense channel next to the hypothetical paragraph). Effect: True is the safe choice, False tests whether the rewrite alone is enough. |
| `query.multi_query_prompt` | `prompts/multi_query.md` | Path | What: prompt file with {{question}}, {{title}} and {{n}} placeholders. Effect: wording decides how varied and paper-specific the paraphrases are. |
| `query.hyde_prompt` | `prompts/hyde.md` | Path | What: prompt file with {{question}} and {{title}} placeholders. Effect: wording decides how paper-like the hypothetical paragraph is (and so how close it lands to the real passages in embedding space). |
| `llm.base_url` | `http://localhost:11434/v1` | str | What: OpenAI-compatible endpoint (Ollama now, vLLM later). Effect: none. |
| `llm.api_key` | `ollama` | str | What: key sent to the endpoint; local servers ignore it. Effect: none. |
| `llm.model` | `qwen3:8b` | str | What: model name as the server knows it. Effect: the biggest single lever on answer F1, latency and VRAM; compare candidates with the model_* configs. |
| `llm.temperature` | `0.0` | float | What: sampling randomness. Typical: 0-0.3 for QA. Effect: 0 makes runs repeatable; higher adds variety and run-to-run noise in metrics. |
| `llm.max_tokens` | `512` | int | What: max tokens the model may generate. Typical: 256-1024. Effect: too low truncates the JSON (error_rate rises); higher only matters if the model rambles. |
| `llm.context_window` | `16384` | int | What: context length the server runs with (Ollama: OLLAMA_CONTEXT_LENGTH). Only used for a warning. Typical: 8192-32768. Effect: prompts longer than the real window are silently cut by Ollama and scores collapse; the report warns at 95%. |
| `llm.timeout_s` | `120.0` | float | What: seconds before one request is abandoned. Typical: 60-300. Effect: too low turns slow answers into errors; too high hides a stuck server. |
| `llm.max_retries` | `3` | int | What: attempts per request on connection/timeout/5xx errors. Typical: 2-5. Effect: higher survives a flaky server but fails slower; bad answers are not retried. |
